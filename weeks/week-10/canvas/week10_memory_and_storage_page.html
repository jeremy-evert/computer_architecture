Week 10 - Memory & Storage: A Worked Example on a Real Machine

This page walks through one real computer, start to finish: what memory and storage it has, what each layer costs in dollars, how fast each layer is, and what our experiments actually measured. Read it before Wednesday's lab. Nothing here is a number to memorize. Look for the shapes, then check them against your own machine.

Machine used: the instructor's desktop PC (an Intel Core i7-8700K, running Windows with Ubuntu Linux inside it through WSL2). Your machine will differ. That is the point.

1. The central question

Why do we need layers of memory, and what does crossing a layer feel like?

Short answer: faster storage takes more room per bit, sits closer to the processor, and costs far more. Nobody can afford to build a whole computer out of the fastest layer. So we stack small, fast layers on top of big, slow ones.

What makes the small fast layers pay off is locality: programs tend to reuse data they just used, and to touch data close to what they just touched.

We can put one number on how well a layer is working, the average memory access time (AMAT):

[[EQ:\text{AMAT} = t_{\text{hit}} + (\text{miss rate}) \times (\text{miss penalty})]]

In plain text: AMAT = hit time + (miss rate × miss penalty).

Small illustrative example (made-up numbers, not a measurement): a hit takes 1 time unit, 1 access in 10 misses (miss rate 0.1), and each miss adds 5 units. Then AMAT = 1 + 0.1 × 5 = 1.5 units.

Tools that told confident untruths (good practice for the Critique lens)

  • lsblk said ROTA=1 (spinning disk) for every disk, even the one that lives on an NVMe SSD. The disk it was looking at is a virtual disk.
  • The IronWolf drives report BusType: RAID because they sit behind the motherboard's RAID controller.
  • Our disk experiment printed a filesystem type of 0x1021997. That is 9p, the file-sharing layer WSL2 uses to reach Windows drives. It is not the disk's own filesystem.
  • free, df, and our inventory program report the virtual machine's view, not the host's hardware.

Ask of every number: who is reporting this, and what are they actually looking at?

Why the L1 cache is split, and why L1/L2 are private but L3 is shared

  • L1d vs L1i: in one cycle the core fetches an instruction and also loads or stores data. Two separate caches mean two separate paths, so they do not get in each other's way. Below L1, caches are unified (instructions and data together).
  • Private L1/L2: they must be tiny and close to be fast. Sharing would add wire length and waiting in line.
  • Shared L3: it is already slower, so sharing costs little and buys flexible capacity and fast sharing between cores. Physically it is six 2 MiB slices connected by a ring; logically it is one cache.

4. Typical latency ladder (teaching values, NOT measurements)

These are round numbers for orientation only. At 3.7 GHz one cycle is about 0.27 ns. The last column rescales time so that one cycle feels like one second.

RAM (DDR4-3000, CL15)about 300about 60-90 nsabout 5 minutes
NVMe SSDabout 300,000about 50-100 µsabout 3.5 days
Hard drive (5,900 rpm)about 40,000,000about 10-15 msabout 1.3 years

Why each step costs more:

  • Inside the chip: distance across the chip, bigger arrays to search, address translation (the TLB), and hops around the ring to the right L3 slice.
  • RAM: now you leave the chip. DRAM has to open a row (about 10 ns), read a column (about 10 ns), and sometimes close another row first (about 10 ns).
  • Storage: it is no longer one instruction. It is a request through the operating system, the filesystem, a driver, and the device (and under WSL, the virtual machine and 9p as well).
  • Hard drive: the only layer limited by moving metal. Half a rotation at 5,900 rpm is about 5.1 ms.

RAM bandwidth ceiling for dual-channel DDR4-3000: 3000 MT/s × 8 bytes × 2 channels = 48 GB/s.

The first two steps land near the advertised L1 and L2 sizes. The last one does not: the steep rise begins at roughly half of the advertised L3 size. That is the Critique lesson. A measured cliff is evidence about this run on this machine, not a way to read off a spec sheet.

5.2 The cache line (experiment 02)

We read memory with bigger and bigger strides (jumps between reads). The cost per access climbs as the stride grows toward the 64-byte line size, keeps climbing a bit past it, and levels off around 256 to 512 bytes. Hardware that fetches neighboring lines can blur a sharp knee, so we read this as "the cost rises across the cache-line region", not as a single clean edge.

5.3 Registers (experiment 01)

The same arithmetic loop took about 0.55 ns per step with the running total in a register, and about 1.65 ns per step when the total was forced through memory with volatile. That is about 3 times slower. The 1.65 ns is close to the L1 time from 5.1, so two different experiments point at the same number.

5.5 First touch (experiment 05, 512 MiB, 4 KiB pages)

The first time a program touches a page of fresh memory, the operating system has to find a page, fill it with zeros, and map it (a "page fault"). That cost about 1,600 ns per page here. Touching the same pages a second time cost about 9 to 10 ns per page. Asking for the pages up front with MAP_POPULATE moves the work earlier: about 830 ns per page, paid inside the memory request. Transparent huge pages were set to madvise, so arrays used ordinary 4 KiB pages.

5.7 Network, on one machine (experiment 07, loopback)

A plain function call: about 1.4 ns. A round trip between two processes through pipes: about 65 µs. A round trip over loopback TCP: about 80 µs. Talking to another process costs about as much as one NVMe read. (65 µs is slow for pipes; the virtual machine layer is a plausible but unproven reason.) Loopback is not a real network: there is no wire and no switch.

5.8 Repository (experiment 08)

The program computes the same object id that git hash-object would, and it matched. A git repository stores every version as a small file named by its hash. We timed 2,000 small records stored two ways, with the scratch folder on the Linux home folder:

StoreTime for 2,000 records (about)
one plain file, no sync2.3 ms
one plain file, one sync at the end7 to 8 ms
one file per record (git-loose-object style), no sync110 ms
one file per record, sync after every file5.4 to 5.7 seconds

Remembering every version, and being sure it is saved, is measurably more expensive than appending to one file. In a throwaway repository with two commits we counted 6 objects: 2 file contents, 2 directory listings, and 2 commits. Note: our "loose object" store skips the compression that real git does.

7. Open questions and Critique moments

  1. Why does the steep rise in 5.1 begin near 6 MB instead of at 12 MiB? Some hypotheses, none proven: the translation cache (TLB) covers only about 6 MiB of 4 KiB pages; the L3 is shared with other work on the machine, Windows, and the virtual machine layer; the L3 spreads addresses across slices in a hashed way.
  2. Why is random-dependent about 100 ns in experiment 04 but the RAM plateau is about 80 ns in experiment 03? Probably extra address-translation work with a 256 MB buffer (unproven).
  3. Which layer did you actually measure? RAM-backed /tmp, an ext4 virtual disk, and a 9p share can all sit on the same SSD and give wildly different numbers.
  4. Which price is "the price"? On one listing page, the same CPU appeared at $20, $35, $80, $154, and $300 (2026-10-21).
  5. Who reported this number? A virtual machine and its host can disagree about RAM, disks, spinning-or-not, and bus type.
